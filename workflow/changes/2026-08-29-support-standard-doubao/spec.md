# Spec: 同时支持「豆包」和「豆包工作」

## Requirements

1. 桌面工具必须把标准版「豆包」和「豆包工作」建模为两个独立的目标应用，并能分别识别它们是否安装。
2. 用户必须在应用主题前看到并明确选择当前目标；工具不得在两款都安装时暗中猜测。
3. 同一套主题包必须能通过现有数据驱动主题引擎应用到两款应用，不为单个主题分叉业务逻辑。
4. 实时应用只能启动、退出、激活、注入和恢复用户当前选定的目标，不得误操作另一款应用。
5. 「恢复默认」必须清理当前目标页面中由工具注入的运行时、样式、背景层和标记；不得把删除离线克隆应用当成实时恢复。
6. 工具退出后不再持续注入；重新打开官方目标应用时必须是官方外观。
7. 新增标准版「豆包」支持不得改变「豆包工作」现有的主题注入范围、页面导航后重注入和窗口唤醒行为。
8. 产品名称与主要文案统一为「豆包主题」，官网、README、安装包元数据和桌面应用必须明确写「支持 macOS 版豆包与豆包工作」。

## User experience

- 主界面使用两段式目标选择器：「豆包」和「豆包工作」。它是应用上下文选择，不是主题分类。
- 当两款应用都安装时，首次启动保持现有用户行为，默认选中「豆包工作」；用户之后的选择会作为一个简单偏好持久化。只安装其中一款时直接选中已安装的应用。
- 未安装的目标仍显示产品名，但标记「未安装」并不可用；不用弹窗打断浏览主题。两款都未安装时，「应用主题」不可用，就地说明需先安装豆包或豆包工作。
- 目标选择器提供清晰的选中态、指针悬停态、VoiceOver 名称与状态，并可以用 `Command-1`（豆包）和 `Command-2`（豆包工作）切换。
- 切换目标时，先停止旧目标的 watcher 并清理旧目标的实时注入，再切换上下文；不显示常规成功弹窗。
- 主题预览中的应用名称与欢迎语跟随当前目标，避免选中「豆包」时仍显示「豆包工作」。
- 正常窗口与 720 px 最小宽度都必须保持选择器、主操作、标准红黄绿窗口按钮和键盘焦点可见。

## Technical design

- 在 `crates/skin-core/src/live.rs` 内增加一个小型 `TargetApp` 枚举，只封装两个已存在实现的定值差异：显示名、bundle id、应用路径、可执行文件、AppleScript 名称、进程匹配片段、启动标记、CDP 端口和目标 URL 模式。不新增 Manager、Service、Factory 或插件层。
- 「豆包工作」保留现有端口 `9222` 和 `doubaowork://` / `chrome://doubaowork` 页面模式。标准版「豆包」使用独立端口 `9223` 以及本机安装包已证实存在的 `doubao://` / `chrome://doubao` 页面模式。通用的 side panel / popup 页只能在该端口已识别出所选应用身份后注入。
- `live::run` 接收 `TargetApp` 而不再从全局常量猜测目标。`ensure_running`、`launch_app`、`kill_app`、启动时间标记和 wedge recovery 都使用目标元数据。
- 复用已打开的调试端口前，必须检查该端口的页面是否属于选定目标。如果端口被其他应用或错误目标占用，返回可操作的中文错误，不复用端口、不终止无关进程。
- 增加一个直接的实时恢复函数：在选定目标的匹配页中调用 `window.__doubaoSkinRuntime.destroy()`，删除 `#doubao-skin-style`、`#doubao-skin-backdrop`、`data-skin`及工具增加的图标/输入框标记。该函数只触碰带本工具标记的 DOM。
- `apps/desktop/src/main.rs` 保存当前 `TargetApp`，把它传给应用与恢复函数，并将 active theme 与 target 一起判定，避免在 A 应用中已应用的主题让 B 应用的按钮误显示「正在使用」。
- 偏好只保存一个目标 id，写入现有 `~/Library/Application Support/Doubao Skin/` 目录下的小文本文件；未知值回退到安装检测默认，不引入新依赖。
- 试验性 `protocol_bridge` 继续只使用「豆包工作」的 `9222` 端口和 URL 约束，本变更不扩展其数据边界。
- 离线 clone / PAK 模块保持现有「豆包工作」实验路径，不把它接入双应用主界面。

## Security and privacy

- CDP 只绑定环回地址，两个目标使用不同端口，不向局域网或公网暴露调试接口。
- 目标身份、进程匹配和 URL 匹配全部来自代码内受控常量，不接受主题包、网页或用户文本作为命令参数。
- 目标过滤只识别两款应用的内建页面；不向普通网页标签、附件预览或未知扩展页注入。
- 实时主题逻辑只写入 DOM 样式和工具自有标记，不读取或记录聊天正文、凭据、Cookie、附件、工作区或网络请求。
- 实窗验证使用新建的空白会话或无敏感测试内容；不把个人会话、官方资源或凭据提交到仓库。
- 恢复逻辑不修改官方 app bundle，不要求管理员权限，也不删除用户数据。

## Alternatives and non-goals

- 不采用「两款都安装时自动挑一款」：这会让重启和进程终止的对象不明确。
- 不采用「一次应用到两款」：会同时操作两个客户端，与用户一次选择一个目标的意图冲突。
- 不复制两套 `live.rs` 逻辑：两款应用共享完全相同的 CDP 生命周期，只有少量定值不同。
- 不在本变更中扩展标准版「豆包」的协议桥、模型替换、网络代理、离线克隆、PAK 修改或重签名能力。
- 不改变主题 v2 schema；两款应用的局部 CSS 适配优先在现有 `theme.css` 和语义令牌中完成。

## Areas of concern

- 两款应用可能在后续版本中改变内建 URL、DOM 或设计令牌；当前验收只能对记录在 `verification.md` 的实测版本负责。
- 标准版「豆包」已证实声明 `doubao` URL scheme，且安装包中存在 `chrome://doubao-chat` 与 `doubao://doubao-chat/chat`；但真正可注入的页集仍必须在计划获批后通过实际 CDP 目标验证，不能仅凭字符串认定。
- 两款应用同时运行时，固定端口、进程匹配和目标页验证三层都必须通过；否则应停止并显示错误，不做猜测性恢复。
- 标准版与工作版的导航结构和文案不同，现有图标语义匹配可能只覆盖工作版；验证时必须区分「颜色/背景生效」与「所有可选图标都成功替换」，不诚称后者已完成。
- 当前工作区存在大量与本变更无关的并行改动；实现、测试和验证必须维持目标文件和目标行为边界。

## Acceptance criteria

1. 安装检测正确区分标准版「豆包」与「豆包工作」；两款都安装时显示两个可用目标，只安装一款时不会选中不存在的应用。
2. 目标选择器在正常和最小窗口中都可见、可点击、有悬停/选中/不可用态，`Command-1` / `Command-2` 可用，VoiceOver 标签不依赖颜色表达状态。
3. 选中「豆包」并应用主题时，只有 `/Applications/Doubao.app` 被必要地重启/激活，主对话页出现主题；「豆包工作」的 PID 和页面不受影响。
4. 选中「豆包工作」并应用主题时，只有 `/Applications/DoubaoWork.app` 被必要地重启/激活，现有主对话页、导航后重注入和窗口唤醒行为不退化；标准版「豆包」不受影响。
5. 在两款应用都已启动的情况下往返切换目标，不会复用错误端口、终止错误进程或把已应用状态显示到另一款应用。
6. 「恢复默认」会立即清理当前目标的实时主题标记和样式；退出主题工具并重新打开任一官方应用后都是官方外观。
7. 主题预览、桌面应用名称、安装包、官网和 README 都不再声称「仅支持豆包工作」，并且不将标准版与工作版混为同一应用。
8. Rust 单元/回归测试覆盖两个目标的元数据、安装默认、URL 过滤、端口归属拒绝和恢复 JS；桌面 UI 测试覆盖选择/激活状态与动态预览文案。
9. 对两款应用分别完成一次真实窗口验证：选择目标、应用主题、检查主对话和增量导航后的持续性、恢复默认，并在正常/窄窗口截图中确认布局与文字可读。
10. `./scripts/check.sh rust`、`pnpm --dir apps/web sync && ./scripts/check.sh web`、`./scripts/check.sh workflow` 以及本变更实际触及范围的全部检查通过；`verification.md` 记录实测版本、命令、截图、PID/端口证据、偏差和剩余风险。

## Decision

产品与风险负责人已确认本规格，同意以明确双目标选择、独立进程/CDP 生命周期与真实双应用验证作为设计边界。
