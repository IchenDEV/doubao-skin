# Intent: remember last theme

## Problem

豆皮当前只在用户点击“应用主题”后的本次进程中保存活动主题和 watcher。豆皮窗口关闭或用户重新登录后，活动主题丢失；豆包或豆包工作若通过自身开机启动、Dock、Finder 或桌面图标直接打开，会以没有豆皮主题的普通进程启动。已经选择主题的用户因此不能把“下次仍使用这个主题”当作稳定偏好。

用户对“保持上次主题”和“登录时自动打开豆包”有不同需求：有人希望手动打开豆包后自动恢复主题，但不希望豆包随登录出现；也有人希望登录后直接打开带主题的豆包。两种行为不能由一个含糊的开关绑定。

## Proposed outcome

在 macOS 桌面应用中提供两个职责清楚的开关：

1. “自动保持上次主题”：持久化最后一次成功应用的目标、主题和用户可调参数，并在用户允许的后台生命周期中，于目标应用下次启动时恢复主题。
2. “登录时打开豆包”：作为第一个开关的从属项；只在用户明确开启时，登录后主动启动已选择的目标应用。关闭时后台能力不得自行打开目标应用。

实现复用现有 loopback CDP 启动、身份校验、注入和恢复路径，通过 Apple 支持的用户级登录项机制保持必要的后台生命周期。不得修改、替换或重新签名官方豆包安装包。

## Affected users and systems

- 在 macOS 上使用豆皮给“豆包”或“豆包工作”应用实时主题的用户。
- `apps/desktop` 的设置状态、窗口/后台生命周期和 macOS 打包内容。
- `crates/skin-core` 中目标应用启动、loopback CDP watcher 与持久化配置的共享边界。
- Windows 现有实时应用、CLI、离线克隆、主题格式和 Web Gallery 不改变行为。

## Constraints

- 不修改 `/Applications/Doubao.app`、`/Applications/DoubaoWork.app` 或它们的资源、签名、登录项和用户数据。
- 后台能力必须由用户通过“自动保持上次主题”明确开启，使用用户级、可查询状态、可注销的系统机制；不得安装 root daemon、手写不可管理的全局启动项或要求关闭系统安全功能。
- 两个开关必须保持真实状态：“登录时打开豆包”仅在“自动保持上次主题”开启且后台项获系统允许时可用；注册失败、等待批准或被系统设置禁用时必须给出可执行反馈，不能显示为已生效。
- “登录时打开豆包”关闭时，用户登录、豆皮后台启动、目标应用退出或 watcher 异常均不得主动打开目标应用。用户主动退出豆包后，只等待下一次用户启动。
- 用户直接启动一个未带调试参数的目标应用时，可以为恢复主题执行一次受控重启，但必须先验证 bundle/进程身份、限制为一次、避免重启循环，并在产品说明中诚实保留可能短暂显示默认外观的边界。
- 只连接目标专属的 `127.0.0.1` 端口并复用现有身份校验；不得读取会话正文、Cookie、认证头、附件、工具或工作区数据。
- 最后主题配置必须在成功应用后才提交，采用可恢复/原子写入；主题不存在、损坏、端口被占用或配置版本未知时安全停止，不得反复启动应用或覆盖有效旧配置。
- 用户关闭“自动保持上次主题”时注销后台能力、停止 watcher，并保留当前已注入页面直到用户选择“恢复默认”或目标退出；两个操作的语义不得混淆。
- 遵循现有自签名 macOS 打包边界；任何嵌入式 helper、服务声明和主应用必须在最终包中完整签名并通过实际安装包验证。

## Out of scope

- 修改豆包官方“开机启动”设置，或静默替用户关闭系统设置中的其他登录项；检测到潜在重复启动时只提示用户处理。
- 保证从官方图标启动未带参数的豆包完全没有单帧默认外观；本变更保证最终自动恢复并防止循环重启。
- 新增菜单栏常驻图标、设置页、通知中心消息、自动更新器或通用进程管理框架。
- 同一时间为“豆包”和“豆包工作”分别维持两个独立活动主题；继续沿用当前一次选择一个目标应用的产品模型。
- Windows 开机启动/后台服务；Windows 现有手动应用能力必须保持不回归。
- 改变主题包 schema、CSS、Web 目录、商店协议、离线克隆或实验性协议桥。

## Success signals

- 只有两个用户可见开关；第二项以清楚的从属层级显示，父项关闭时第二项关闭且不可操作。
- 应用主题成功、退出豆皮界面并再次打开后，仍能读取最后成功的目标、主题和透明度；失败的应用尝试不会替换已保存状态。
- “自动保持上次主题”开启、“登录时打开豆包”关闭时，重新登录或单独启动后台项不会打开豆包；用户稍后从官方图标启动后，保存的主题自动恢复。
- 两个开关都开启时，用户登录后由豆皮启动选定目标并自动恢复最后主题；不会与自身产生重复进程或重启循环。
- 用户主动退出目标应用后保持退出；下一次手动启动才恢复主题。
- 关闭自动保持后，系统后台项状态显示为未注册，后续目标应用启动不再被豆皮接管；“恢复默认”仍只清理豆皮拥有的页面状态。
- 自动测试覆盖配置读写/损坏回退、开关依赖、系统状态映射、手动退出不重开、直接启动受控单次重启、错误端口身份和 Windows 无回归。
- 最终签名 macOS App 在正常窗口和当前不可调整的最小窗口中正确显示两个开关；实际登录项注册/注销、手动启动、登录启动、主题恢复和回滚均有可观察证据。
- `./scripts/check.sh all` 与 workflow policy 通过；`verification.md` 记录命令、真实窗口/登录项证据、签名检查、残余闪白边界和 fresh-context 最终 verdict。

## Open questions

- 产品代码开始前，在 spec 中用最小原型确认现有 GPUI/macOS 打包链最适合嵌入轻量 Login Item helper，还是注册指向现有无界面运行模式的用户级 Agent；选择必须以可签名、可注销、不会显示主窗口为准，不能仅凭源码推断系统已接受注册。
- 当前应用没有独立设置页。两个开关在现有主题操作区域中的准确位置、说明文案和授权失败反馈，需要在 spec/plan 中基于现有窗口密度确定，并通过真实窗口验证而不是扩大导航结构。

## Decision

等待产品与风险负责人明确批准本 intent 后进入 spec；当前未授权产品代码、打包配置或系统登录项修改。
