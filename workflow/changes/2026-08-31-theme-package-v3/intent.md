# Intent: 主题包 v3 多宿主兼容规范

## Problem

当前 `schemaVersion: 2` 主题包没有声明适用的目标应用，也没有正式区分共享样式与宿主专用样式。豆包和豆包工作直接加载同一份 `theme.css`，WorkBuddy 则绕过这份 CSS、仅从结构化字段生成宿主适配 CSS。结果是主题列表只能用引擎内的硬编码判断兼容性，主题作者无法准确表达“支持哪些应用、共享哪些视觉定义、每个应用还要加载什么”，用户也无法在应用前知道兼容程度。随着第三个宿主加入，继续依赖隐式回退会让视觉割裂、误加载和兼容性声明失真。

## Proposed outcome

制定 `schemaVersion: 3` 主题包规范，把一款主题的跨应用能力声明为可验证的数据契约：主题必须显式声明支持 `doubao`、`doubao-work`、`workbuddy` 中的哪些目标；共享的结构化视觉令牌和共享 CSS 只定义一次；每个目标可以声明自己的结构化覆盖、CSS 入口和资源覆盖。加载器依据清单按固定顺序合并共享层与当前目标层，只加载当前目标明确声明的文件，不再把“某些颜色碰巧生效”视为兼容。

该规范要允许一款主题同时覆盖多个目标，也允许只支持其中一个目标；支持范围、实际可加载文件和用户界面中的兼容提示必须来自同一个主题清单事实源。仓库外已安装或第三方 v1/v2 主题继续按明确的旧版兼容策略运行，不要求立即迁移。

产品负责人随后把交付范围扩展为：完成 v3 引擎与工具链后，将仓库 `themes/` 中的全部内置主题迁移到 v3，而不是只提供格式规范或只迁移鲸鱼娘。当前基线为 30 个 v2 主题；迁移完成时仓库不得继续混合分发 v2 内置主题。

## Affected users and systems

- 创建、维护和分发主题包的主题作者。
- 在豆包、豆包工作和 WorkBuddy 之间选择主题的用户。
- `design/theme-standard` 中的主题包标准、JSON Schema、示例和迁移说明。
- `crates/skin-core` 中后续需要实现的 manifest 解析、能力判定、CSS/资源解析、合并顺序和安全校验。
- `apps/desktop` 与 `apps/web` 中后续需要展示的目标适用范围、兼容状态和不可应用原因。
- 主题作者 CLI、主题打包器、在线目录同步与安装校验。
- `themes/` 中当前全部 30 个内置主题及其 manifest、CSS、预览、背景、图标和来源信息。

## Constraints

- 正式目标标识固定使用 `doubao`、`doubao-work`、`workbuddy`；用户口语中的 “Walker Bundle” 不作为清单标识或别名写入规范。
- 主题包仍是数据包。目标差异必须由 manifest、CSS 和包内资源表达，桌面端不得按主题 ID 增加分支。
- 加载器只允许加载 manifest 明确引用、位于主题目录内并通过校验的相对路径；拒绝目录穿越、远程 CSS、任意脚本、HTML、网络导入和未声明文件的隐式发现。
- CSS 必须按目标隔离并具有确定的层叠顺序。目标专用 CSS 不得进入其他应用，共享 CSS 不得包含只能在单一宿主成立的选择器或私有变量。
- 结构化共享字段继续承担跨应用视觉语义；宿主 CSS 只补充宿主 DOM 或变量差异，不得把整套主题重新复制三份作为推荐用法。
- 目标声明必须可由 JSON Schema、打包器和运行时独立验证。声明支持某目标但缺少其必需入口或引用不存在资源时，主题包必须安装失败或明确判定为不兼容，不能静默降级后仍显示“支持”。
- v1/v2 兼容行为必须确定、可测试、可解释；升级到 v3 不得让已安装旧主题突然无法用于其原本可用的豆包目标。
- 主题包版本 `version` 与格式版本 `schemaVersion` 继续分离；前者用于主题自身发布更新，后者决定清单语义。
- 不改变三款官方应用的安装包、签名、用户数据、进程安全边界或 CDP 目标识别策略。
- 规范必须覆盖深浅色变体、预览、背景、字体和图标等资源如何在共享层与目标层之间继承或覆盖，避免只解决 CSS 文件名。
- 30 个内置主题都必须迁移并保留当前可见身份、预览、许可来源和三目标能力，不允许用删除主题、隐藏主题或减少目标支持来缩小迁移工作量。
- 批量迁移必须建立在 v3 Schema、解析器、CSS 校验器和迁移测试通过之后；不得仅批量替换 `schemaVersion` 或机械移动字段后宣称完成。

## Out of scope

- Intent/Spec 阶段只定义契约，不提前修改产品代码；在 Spec 与 Plan 获批后的实现阶段，v3 解析器、工具链、产品兼容展示和全部内置主题迁移均属于交付范围。
- 不把主题系统扩展为可执行插件、JavaScript 注入框架、任意 Electron 应用适配平台或第三方应用商店协议。
- 不承诺一个主题在三个宿主中像素级一致；规范保证的是声明真实、合并确定、隔离安全和各宿主可独立完善。
- 不允许主题作者覆盖目标识别、进程启动、端口、恢复逻辑或运行时安全策略。
- 不在 v3 中支持远程依赖、CSS `@import`、运行时下载字体/图片、包间继承或主题组合。
- 不强制 30 个主题都创建 WorkBuddy 专用 CSS；共享结构和内置适配器已经通过实窗验收时可以使用空的 `targets.workbuddy`，但三目标声明与逐主题验证不能省略。
- 不自动改写用户自行安装的主题、主题商店中尚未进入本仓库的第三方包或其他仓库中的 v2 主题；它们继续使用旧版兼容路径，作者可主动迁移。

## Success signals

- 规范给出一个完整、可执行的 v3 JSON 示例，能分别表达仅支持一个目标、多个目标以及三个目标全支持。
- 规范明确共享结构字段、共享 CSS、目标结构覆盖、目标 CSS 和目标资源覆盖的职责与固定合并顺序。
- 规范定义“不支持”“支持但只有共享语义”“带目标专用适配”三类机器可判定状态，且产品不得把未声明或校验失败的目标显示为可应用。
- 对 `doubao`、`doubao-work`、`workbuddy` 的目标 ID、CSS 作用域、文件路径、继承、冲突、缺失文件、未知目标和未知字段均有确定规则。
- v1/v2 到 v3 的兼容矩阵和迁移示例明确；鲸鱼娘可以作为示例被表达为共享视觉层加 WorkBuddy 专用 CSS，而不复制整个主题。
- 规范包含安全限制、资源打包规则、主题商店目录需要导出的兼容元数据，以及后续实现可直接转化为自动测试的验收条目。
- 评审者仅阅读规范即可回答：一个主题支持哪些应用、当前应用会按什么顺序加载哪些文件、哪些值被覆盖，以及错误时为何拒绝加载。
- 当前 30 个内置主题全部通过 v3 Schema、打包、目录同步和三目标解析检查；合并时 `themes/` 中不存在残留的 v1/v2 manifest。
- 每个内置主题在豆包、豆包工作和 WorkBuddy 的浅色/深色实际窗口中都有可复核结果；失败主题必须修复，不能通过撤掉目标声明规避当前兼容能力。

## Open questions

以下设计点留给 Spec 阶段给出单一结论，不作为开放式实现选择长期保留：

1. manifest 采用顶层 `targets` 映射还是“共享层 + targets 映射”的嵌套结构；目标是让支持范围与目标入口不可互相矛盾。
2. 是否允许只靠共享结构字段声明某目标可用，还是每个受支持目标都必须显式选择一种适配模式。
3. 共享 CSS 与宿主 CSS 的准确加载顺序、同层多文件顺序，以及结构化字段生成 CSS 在层叠中的位置。
4. v2 的必需 `theme.css` 在 v3 中应改为可选还是由显式入口取代；不能同时保留两个互相冲突的默认入口。
5. 目标资源覆盖应采用通用对象覆盖，还是只允许对背景、字体、图标等已知资源类别覆盖。
6. 未知目标 ID、未知适配模式和未来新增宿主在旧版加载器与新版加载器中的前向兼容行为。

## Decision

产品负责人已明确接受本 Intent，并在 Spec 评审期间明确追加“迁移现有全部主题”。批准范围因此包括建立 v3 多宿主契约，并在后续 Spec 与 Plan 获批后迁移仓库全部内置主题；当前仍未批准具体 JSON 结构或开始实现。
